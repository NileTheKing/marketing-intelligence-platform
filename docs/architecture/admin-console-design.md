# 관리자 콘솔 디자인

Status: active

관리자 화면은 `console.css`와 `fragments/console_sidebar.html`을 기준으로 맞춘다.
참고 화면은 전체 개요(`global-dashboard.html`), 캠페인 관리(`admin.html`),
활동 대시보드(`dashboard.html`), 증분 효과(`incrementality.html`)다.

## 시각 기준

- 배경 `#f7f7f5`, 흰색 카드, 테두리 `#e7e6e2`, 카드 모서리 10px.
- 강조색은 `#2b5cd6`. 위험은 `--low`, 활성 상태는 `--ok`, 나머지 상태는 회색.
- Pretendard, 본문 13px, 페이지 제목 19px. 수치는 `.num`, 표의 숫자는 오른쪽 정렬.
- 왼쪽 공통 사이드바와 `.topbar`, 섹션 제목 `.cat`, 내용 `.card`로 구성한다.
- KPI는 `.kpis`, 차트는 `.card.panel`, 표는 공통 table 스타일을 쓴다.
- 버튼, 상태 표시, 툴바, 드롭다운, 기간 선택, 입력 필드와 모달은 `console.css`에서 공유한다.
- 그림자는 드롭다운에만 사용한다. 큰 아이콘, 이모지, 그라데이션과 색 배경 히어로는 쓰지 않는다.
- 새 문구는 한국어로 작성하고 나열에는 쉼표를 쓴다.

## 차트와 수치

Chart.js 4.4.1을 사용한다. 기본 막대는 `#dcdad4`, 강조할 막대는 파랑이다.
범례와 격자, y축을 숨기고 시간대 x축은 6시간 간격으로 표시한다.
금액 표기는 `global-dashboard.js`의 `formatWon`을 따른다. 1억 미만은 원 단위,
1억 이상은 억과 만원 단위를 쓴다. ROAS 100% 미만은 빨강, 매출이 없으면 `매출 없음`이다.
조회할 수 없는 데이터는 실제 0과 구분해 안내와 `-`로 표시한다.

## 동작 유지와 확인

스타일 개편에서는 요청 경로, 폴링 주기, 요소 id와 이벤트 연결을 유지한다.
이전 레이아웃을 제거할 때 `common.js` 등 기존 스크립트 의존성도 확인한다.
챗봇과 기존 폼에서 사용하는 Tailwind, Font Awesome은 유지한다.

로컬 Compose 프로젝트는 `docker`다. Core만 재빌드하고 `--no-deps`로 실행한다.
공유 MySQL과 Redis는 재생성하지 않는다. 기존 시연 데이터가 있으면 초기화하지 않는다.
1440px 폭에서 기준 화면과 각 화면을 비교하고, 목록 조회, 기간 변경,
폼 열기와 닫기, 수정 값과 유형별 입력 전환을 확인한다.

## 탐색 범위

- 캠페인 대시보드, 쿠폰, 행동 이벤트, 캠페인 생성·수정 폼과 활동 생성 화면은 공통 콘솔을 사용한다.
- 관리자 진입 `/admin`은 전체 개요로 연결한다. 데이터 API와 접근 권한 정책은 별개다.
- 코호트는 배치 분석용 보조 화면이다. 외부 데모 기본 탐색에는 추가하지 않는 것을 권장한다.
- 모니터링은 내부 운영 화면이다. 외부 데모에 공개하지 않고 기존 권한을 유지하는 것을 권장한다.
  두 화면은 이번 디자인 작업에서 개편하거나 권한·노출 정책을 변경하지 않는다.

## 외부 심사용 데모의 목적과 재구성 방향

2026-10-26 논의 기록. 아래 재구성 방향은 검토 사항이며, 화면에 적용한 설계가 아니다.

### 현재 제공 범위

기존 개편은 기능, API와 메뉴 구성을 존중하면서 관리자 화면의 디자인을 통일한 작업이다.
심사자가 무엇을 어떤 순서로 살펴보게 할지까지 재구성한 것은 아니다.
현재 코드의 사이드바에는 개요, 증분 효과, 캠페인, 쿠폰, 행동 이벤트가 있다.

2026-10-24 배포 확인 당시에는 MySQL 기반 캠페인, 구매·매출 조회와 발송 완료된 실행의
증분 분석을 이용할 수 있었다. Elasticsearch와 Connect는 기동하지 않아 방문·행동
지표는 조회할 수 없었다. 이 기록을 현재 VM의 실시간 상태 확인으로 해석하지 않는다.
시연 데이터와 배포 근거는 [운영 기록](../operations/oracle-compose-baseline-runbook.md)에 둔다.

공통 데모 배너에는 다음 안내를 반영했다.

> 읽기 전용 데모입니다. 제한된 서버 자원으로 일부 분석 서비스를 중지해, 방문·행동 지표는 표시되지 않습니다. 캠페인과 구매·매출 데이터는 확인할 수 있습니다.

### 화면을 공개하는 이유와 한계

데모는 구현한 기능의 완성도와 업무 흐름을 직접 확인하는 용도다. 화면 사이의 일관성,
캠페인과 활동의 연결, 쿠폰 발송 이력과 성과 조회가 자연스럽게 이어지는지 보여준다.
TPS, 트랜잭션 정합성, SQL 개선 효과는 화면만으로 입증할 수 없으며, 해당 실험 기록과
포트폴리오가 근거를 맡는다. 시연용 합성 매출을 실제 사업 성과로 설명하지 않는다.

핵심으로 설명한 행동 분석 기능이 계속 빈 화면으로 보이면 프로젝트 이해와 완성도
판단을 방해할 수 있다. 제한 안내를 붙이는 것만으로 탐색 경험까지 해결된 것은 아니다.

### 다음 개편에서 판단할 기준

- 첫 화면에서 서비스의 목적과 지금 확인할 수 있는 범위를 이해할 수 있게 한다.
- 캠페인 → 활동 → 쿠폰 발송 이력 → 구매 성과라는 흐름이 실제 제공 기능으로
  이어지는지 먼저 확인한다. 이 순서는 제안이며 아직 구현한 탐색 경로가 아니다.
- 조회 불가능한 지표가 많은 화면은 기본 탐색에서 제외할지, 제한을 명확히 표시할지
  화면별로 판단한다. 메뉴를 숨기는 결정과 실제 관리자 기능·권한 변경은 구분한다.
- 작동하는 기능만으로 서비스 흐름이 충분히 설명되는지 확인하고, 부족한 부분만
  보완한다. 없는 기능을 있는 것처럼 표시하거나 누락 지표를 가짜 값으로 채우지 않는다.

새 디자인을 만들기 전에 기존 메뉴, 화면별 제공 데이터, 이동 경로를 대조해 재구성 범위를
정한다. 현재 운영 제한에 맞춘 데모 구성과 서비스 자체의 기능 설계를 혼동하지 않는다.

## 2026-10-24 로컬 확인

- 1440px에서 전체 개요와 캠페인 관리 기준 화면을 비교하고, 캠페인 대시보드,
  쿠폰 목록과 생성·수정 팝업, 이벤트 목록과 생성 폼, 캠페인 생성·수정 팝업,
  활동 생성 화면과 활동 수정 팝업을 확인했다. 실제 시연 데이터로 조회하며 저장·삭제는 하지 않았다.
- 기간 변경과 SSE 재연결, 팝업 열기·닫기, 기존 수정 값,
  활동 이름 미리보기, 상품·쿠폰 검색, 쿠폰 지급 방식별 필수 입력 전환을 확인했다.
- 기존 관리자 데모 통합 테스트 4개가 통과했다. `/admin`의 개요 리다이렉트도 반영했다.
  테스트 JWT는 로컬 확인에만 사용하고 값은 기록하지 않았다.
- 화면 스크립트의 기존 `fetch` 요청 표현과 폼 요소 id를 대조했다.
  활동 생성 스크립트가 참조하는 `.lg:col-span-8` 클래스와 `header h1` 구조도 유지한다.
- 당시 발견한 이슈(아래 후속 수정 완료): 로컬 시연 데이터의 증분 분석 API는 기존 HTTP 409를 반환했다.
  증분 분석의 기본 진입은 가장 큰 실행 ID를 선택하지만, 로컬의 최신 실행 7은
  `AWAITING_APPROVAL`이므로 발송 완료 조건을 만족하지 못한다. API는 이 경우 409를
  반환한다. 발송 완료되고 대조군이 있는 실행과 구분해 화면에 안내하는 후속 수정이 필요하다.
- 기존 쿠폰 활동 수정은 `Helpers.applyCouponEdit` 호출과 모듈의 공개 함수 위치가 달라
  초기화 오류가 발생한다. 저장 시의 `Helpers.serializeCouponDelivery`도 같은 참조 오류다.
  실제 함수는 `CampaignActivityModule`의 최상위 공개 함수다. 두 문제는 디자인 개편
  범위에서 기능을 바꾸지 않고 남겼다.

## 2026-10-24 기능 오류 후속 수정

- 증분 분석 기본 진입과 실행 선택 목록은 발송 완료, 발송 시각 존재, 대조군 존재 조건을
  만족하는 실행만 사용한다. 조건에 맞는 실행이 없으면 빈 상태를 표시한다.
- 승인 대기 실행이나 존재하지 않는 실행의 직접 링크는 조건 안내와 분석 화면 링크를
  표시하고 분석 API를 호출하지 않는다. API 자체의 409 업무 조건은 유지한다.
- 활동 생성·수정 화면은 모듈 최상위의 `applyCouponEdit`와
  `serializeCouponDelivery`를 직접 참조하도록 수정했다.
- 페이지 데이터 및 증분 계산 Java 테스트 6개, 공유 JS 모듈과 호출부 계약 테스트 3개가
  통과했다. JavaScript 구문 검사와 배포 JAR 빌드도 통과했다.
- VM 배포 후 기본 진입이 실행 4를 선택하고 선택 목록에는 실행 4, 3, 2, 1만 표시됨을
  확인했다. 승인 대기와 없는 실행의 직접 링크는 안내를 표시하고 분석 스크립트를 로드하지 않는다.
  배포된 활동 편집 스크립트의 두 함수 참조와 데모 변경 요청 403도 확인했다.
